# HackCanton Season 4 — Verified Public Rules Snapshot

_Last verified: 7 October 2026 from the current AppsFactory Hackathons page._

This file records only public facts that can be verified now. Logged-in portal instructions and later organizer updates override this snapshot.

## Public schedule

- Registration & Team Formation: **24 Sep → 12 Nov 2026**
- Opening ceremony: **12 Nov 2026, 12:00 UTC**
- Delivery/build phase: **13 Nov → 6 Dec 2026**
- Submission deadline: **6 Dec 2026, 23:59 UTC**
- Closing ceremony: **7 Dec 2026, 12:00 UTC**
- Async judging: **7–13 Dec 2026**
- Finalists announced: **14 Dec 2026**
- Grand Final: **16 Dec 2026, 14:00 UTC**
- Finalist field: **Top 5–10**
- Prize pool: **up to $50,000 in cash & credits**

## Public participation rules

- Everyone can participate.
- Solo participation is allowed; teams are also allowed.
- Participation is free.
- Existing code may be used if it complies with the competition rules.
- A project can enter up to two tracks.
- The project must be built on the Canton Network.
- Public materials advertise DevNet environment/support.
- AI integration is encouraged where it adds real value; it is not treated here as mandatory.

## Track selected for CommitLedger

**Primary: Real-World Asset (RWA) & Business Workflows**

Public expected output:
1. MVP with at least one end-to-end workflow: create → update status → transfer/fulfill → audit/report.
2. Lightweight role-based UI.
3. One-page business brief covering ICP, use case, who pays, and why Canton.
4. Short pilot plan with 2–3 steps and required integrations.

CommitLedger maps directly:
- create → Bounty;
- update → Claim + Pull Request;
- fulfill → verified settlement;
- audit/report → SettlementReceipt + Evidence Passport.

## Track strategy

Use one primary track unless a second track adds a clear prize advantage without diluting the story. Do not enter Open Track merely for extra surface area; the public page notes that it has a smaller prize pool than core ecosystem tracks.

## MainNet / DevNet integrity

The public FAQ wording we could verify establishes that the project must be built on Canton, but does not establish a separate requirement that the final proof must be on MainNet. Therefore:
- do not claim MainNet unless actually used;
- target authenticated Canton DevNet proof if organizer access is available;
- preserve the existing reproducible local Canton proof as a fallback/engineering artifact;
- live portal or organizer instructions override this interpretation.

## Submission integrity

- Do not claim DevNet until a successful authenticated DevNet run is captured.
- Do not claim customers, revenue, production transfers, or adoption without evidence.
- DEMO_CREDIT remains non-production test value.
- Existing code is disclosed; Season 4 work must be clearly separated in Git history and submission copy.
